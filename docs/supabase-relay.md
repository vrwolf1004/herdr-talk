# Supabase 연동 설계 (인터넷 채팅)

- 작성: 2026-11-09
- 상태: **설계 초안. 구현 전.** 아래 "결정 필요" 항목을 정한 뒤 구현한다.
- 관련: [rust-roadmap.md](rust-roadmap.md) 의 relay 단계, [encryption-protocol.md](encryption-protocol.md), [todo.md](todo.md) 의 "Chat across the internet through Supabase".

## 목표와 범위

- 목표: 같은 LAN 이 아닌 PC 끼리 채팅한다.
- 범위: 메시지 중계와 상대 키 조회. 채팅 내용은 서버가 읽지 못한다 (종단 암호화).
- 범위 밖 (1차): 파일 전송, 오프라인 메시지 이력, 폰 직접 연결, 데스크톱 앱.

## 기본 원칙

1. **서버는 평문을 보지 않는다.** 메시지는 Noise 로 암호화한 뒤 보낸다. 서버에는 암호문만 간다.
2. **서버는 신뢰하지 않는다.** 서버가 상대 키를 바꿔 끼워 넣을 수 있으므로, 키 확인은 LAN 과 같은 `/trust <코드>` 지문 비교로 한다. 서버 조회값만으로 신뢰하지 않는다.
3. **service_role 키는 클라이언트와 저장소에 두지 않는다.** 플러그인과 앱에는 publishable(anon) 키만 넣는다. 접근은 RLS 로 막는다.
4. **기본은 저장하지 않는다.** 현재 LAN 판과 같다 ("메시지는 저장되지 않는다"). 저장은 결정 항목이다.
5. **토큰과 비밀키는 로그와 화면에 내지 않는다.** 설정 파일에도 비밀값은 두지 않는다.

## 구성 (안)

```text
플러그인 (herdr-talk)                    Supabase
  talk-core                               ├─ Realtime (채널) : 암호문 중계
  ├─ Noise 암호화/복호화  ──WebSocket──▶  ├─ Postgres
  └─ 키 등록·조회 (HTTPS)  ───────────▶  │    peers (공개키, 표시 이름, 마지막 접속)
                                          └─ RLS: 본인 행만 쓰기, 공개 키만 읽기
```

- 전송: Supabase Realtime 채널 (WebSocket). 방(채널) 이름은 상대 쌍에서 파생한 값으로 한다 (예: 두 공개키 해시를 정렬해 합친 값). 채널 이름만으로 누가 누구와 대화하는지는 서버가 알 수 있다 (메타데이터, 아래 "한계").
- 키 등록: 플러그인 시작 시 자기 공개키와 표시 이름을 `peers` 에 upsert. 쓰기는 자기 공개키 행에만 허용 (RLS).
- 상대 찾기: 공개키를 알고 있을 때만 대화한다. 목록 공개는 1차에서 하지 않는다 (아래 결정 항목 3).
- 연결: 기존 LAN 과 같은 Noise IK. 상대 공개키는 `/trust` 로 확인된 것만 쓴다.

## 확장모듈 구성 (2026-11-09 요청)

- Supabase 연동은 `talk-core` 에 직접 넣지 않고 **확장모듈(transport 모듈)** 로 만든다. LAN 과 relay 는 같은 인터페이스를 쓰는 별개 모듈이다.
- **채팅(대화방) 단위로 모듈을 고른다.** 한 대화는 한 모듈에 묶인다 (LAN 대화 또는 relay 대화). 같은 상대라도 경로마다 별도 대화로 본다.
- 공통 인터페이스 (개념):
  - `connect(peer)`: 상대와 연결 준비 (LAN 은 주소 확인, relay 는 채널 구독)
  - `send(peer, ciphertext)` / `recv() -> (peer, ciphertext)`: 암호문만 주고받는다
  - `peers()`: 이 모듈에서 알 수 있는 상대 목록 (LAN 은 UDP 발견, relay 는 키 조회 결과)
  - `close()`: 연결 정리
- 암호화(Noise), `/trust` 지문 확인, 화면 표시는 모듈 밖 공통 코드가 맡는다. 모듈은 암호문 전달만 책임진다.
- 모듈 등록은 설정으로 켠다. relay 설정이 없으면 relay 모듈은 로드되지 않는다.
- **적용 대상 3곳 (2026-11-09 요청)**: Rust TUI (`herdr-talk`), Rust GUI (`herdr-talk-gui`), Python 판 (`talk.py`). 세 곳 모두 같은 relay 기능과 같은 설정 항목을 가진다.
  - Rust TUI 와 GUI 는 `talk-core` 의 relay 모듈을 같이 쓴다. 구현은 한 번만 한다.
  - Python 판은 별도 구현이다. 같은 와이어 형식(암호문 봉투, 채널 이름 규칙, 키 등록 형식)을 따라야 한다. 형식은 문서로 먼저 고정하고 세 판이 같은 테스트 벡터를 통과하게 한다.
  - 단축키 이름은 세 곳에서 같게 한다 (기존 `Ctrl+P` 패턴과 충돌 없는 키로 정한다).
  - 설정 저장 위치는 각 판의 state 폴더 안에 둔다. 비밀값(토큰, 키)은 평문 로그에 찍지 않는다.
- 확장모듈 구조 확정 전에는 기존 LAN 경로를 바꾸지 않는다. 인터페이스로 감싸는 리팩터링은 relay 구현과 함께 한 번에 한다.

## Rust 쪽 작업 (구현 시)

- `talk-core` 에 relay 클라이언트를 추가한다 (WebSocket 클라이언트, HTTPS 클라이언트). 현재 talk-core 는 네트워크를 UDP·TCP 로만 쓴다.
- 플러그인 의존성이 늘어난다. 바이너리 크기와 빌드 시간을 확인한다.
- 설정: 프로젝트 URL 과 publishable 키를 설정 파일 또는 환경 변수로 받는다. 값이 없으면 relay 는 꺼진 상태로 둔다.
- LAN 경로는 바꾸지 않는다. relay 는 추가 경로다.

## 보안 체크리스트 (구현 전 확인)

- [ ] `service_role` 키가 저장소, 로그, 빌드 산출물에 없음 (`git grep` 으로 확인)
- [ ] `peers` 테이블 RLS: 쓰기는 본인 공개키 행만, 읽기는 공개키·표시 이름만 (지문·IP·접속 기록 없음)
- [ ] Realtime 채널 접근 정책: 두 공개키 중 하나라도 맞아야 구독 가능. 아무 채널이나 구독 불가
- [ ] 키 바꿔치기 검증: 처음 보는 키는 `/trust` 전까지 "아직 확인 안 됨" 으로 표시 (LAN 과 같은 규칙)
- [ ] 저장을 켜면 암호문만 저장하고, 보존 기간과 삭제 방법을 정한다
- [ ] 로그에 메시지 본문, 키, 토큰이 찍히지 않는다
- [ ] 요청 한도와 스팸 방지 (LAN 의 발신자별 제한과 같은 취지). Supabase 쪽 한도 설정 확인

## 한계 (사용자에게 알려야 할 것)

- **메타데이터는 보인다.** 서버는 누가 어떤 채널에 접속했는지, 메시지 크기와 시각을 안다. 종단 암호화는 내용만 보호한다.
- **키 확인은 사람이 한다.** 서버를 믿지 않으므로 처음 대화할 때 지문 코드를 두 화면에서 맞춰야 한다. 생략하면 중간자 공격을 막지 못한다.
- **상대가 오프라인이면 전달되지 않는다** (저장을 켜지 않을 때). 현재 LAN 과 같다.
- **Supabase 가 멈추면 채팅이 멈춘다.** LAN 채팅은 영향 없다.

## 결정 필요

1. **서버 방식**: Supabase (Realtime + Postgres) / Cloudflare Workers + Durable Objects (`rust-roadmap.md` 의 안) / 직접 운영 Rust 서버. 추천 기준: 관리할 서버가 가장 적은 쪽. Supabase 는 인증·DB·Realtime 이 한 곳에 있어 설정이 적지만, 플러그인이 Realtime 프로토콜을 직접 구현해야 한다.
2. **메시지 저장**: 저장 안 함 (현재 방식, 추천) / 암호문을 짧게 보관 (보존 기간 명시) / 장기 보관. 저장을 하면 `todo` 의 "오프라인 이력" 항목과 함께 정한다.
3. **상대 찾기**: 공개키를 직접 받아 입력 (추천, 1차) / 표시 이름 검색 / 초대 링크. 검색을 열면 누구나 사용자 목록을 볼 수 있으므로 1차에서는 피한다.
4. **계정**: Supabase Auth 없이 공개키로만 식별 (추천) / 이메일 로그인. 공개키 방식은 키를 잃으면 새로 등록해야 한다.
5. **비용과 한도**: 무료 한도와 자동 정지 정책을 확인하고, 사용량 알림을 설정한다. (소유자 계정에서 확인)

## 와이어 형식 v1 (구현 기준, 세 판 공통)

- 봉투(JSON 한 줄):
  `{"v":1,"channel":"<hex>","from":"<pk hex>","to":"<pk hex>","ct":"<base64>"}`
  - `pk hex`: X25519 공개키 32바이트를 소문자 hex 64자.
  - `ct`: Noise 전송 메시지 (세션은 Noise IK, 기존 LAN 과 같은 `encryption-protocol.md` 규칙).
- 채널 이름: `hex(SHA-256("herdr-talk-relay-v1" || min(pkA,pkB) || max(pkA,pkB)))`. 두 상대에게 항상 같은 값이 나와야 한다.
- 검증: `v` 가 1 이 아니면 버린다. `from` 이 채널을 만든 두 키 중 하나가 아니면 버린다. `ct` 복호화 실패는 조용히 버린다 (본문 없이 카운트만).
- 테스트 벡터: 고정 키 쌍으로 채널 이름과 봉투 바이트를 만들고, Rust 와 Python 이 같은 값을 내는지 확인한다.
- 서버는 봉투 내용을 검사하지 않는다. 채널 구독 권한만 RLS 와 Realtime 정책으로 막는다.

## 서명 검증 설계 (2026-11-09, 사용자 "서명 검증 진행")

문제: 현재 `x-herdr-pk` 헤더는 인증이 아니어서 publishable 키를 가진 누구나 다른 사람 행을 덮어쓸 수 있다.

결정 (추천안 채택):

1. **쓰기는 Edge Function 만 한다.** `peers` 의 anon·authenticated 쓰기 정책을 전부 없앤다 (select 만 허용). 쓰기는 Supabase Edge Function `put-peer` 가 서버 쪽 service role 로 한다. service role 키는 함수 환경에만 있고 클라이언트에 나가지 않는다 (소유자가 CLI 로 배포할 때 설정).
2. **서명 키를 따로 둔다.** Noise 키 (X25519, 세션·봉투용) 는 그대로 두고, 행 쓰기용 **Ed25519 서명 키**를 하나 더 만든다. 개인키는 state 폴더에 사용자만 읽도록 저장한다 (기존 비밀키 저장 규칙과 같음). 공개키 (32바이트 hex) 는 `peers.pk` 로 쓴다.
3. **서명 대상 문자열 (고정 형식):** `"herdr-talk-put-v1\n" + pk + "\n" + name + "\n" + ts + "\n" + nonce`. `ts` 는 unix 초, `nonce` 는 16바이트 hex.
4. **요청**: `POST {url}/functions/v1/put-peer`, 본문 `{"pk":..,"name":..,"ts":..,"nonce":..,"sig":"<128 hex>"}`. 헤더는 `apikey` 로 publishable 키 (함수 게이트용).
5. **함수 검증 순서**: 형식 → `|ts - now| <= 300` → Ed25519 검증 (`pk` 로) → nonce 재사용 거부 (테이블 `put_nonces(nonce pk, ts)`, 만료 행 정리) → upsert `peers`. 실패는 401 또는 400, 이유는 본문에 넣지 않는다.
6. **조회**는 기존처럼 `peers` select (anon 허용). 조회 결과의 서명은 없다. 이름은 "그 키 소유자가 마지막으로 서명해 쓴 이름" 이라는 뜻만 가진다.

주의 (구현 전 확인):

- Python 판은 표준 라이브러리에 Ed25519 가 없다. `noise.py` 처럼 순수 Python 구현이 필요하고, RFC 8032 테스트 벡터로 검증한다.
- Rust 는 Ed25519 크레이트가 있는지 먼저 본다 (`ed25519-dalek` 등). 새 크레이트는 승인 후 추가한다.
- Edge Function 배포에는 Supabase 계정 로그인이 필요하다 (소유자 몫).
- 재생 방지 테이블과 정리 작업은 SQL 에 포함한다.
- 봉투 (`relay.rs`, `relay.py`) 의 `from`/`to` 는 기존 X25519 키 그대로다. 행 쓰기 서명만 Ed25519 를 쓴다. 두 키의 대응(행 `pk` 가 Ed25519 인지 X25519 인지)은 아래 "결정" 에서 확인한다.

결정 필요 (구현 중 확인):
- `peers.pk` 를 Ed25519 공개키로 쓸지, X25519 공개키로 쓰고 서명키와 묶을지. 추천: Ed25519 공개키를 `peers.pk` 로 쓰고, 봉투용 X25519 공개키를 `peers` 의 별도 컬럼 `noise_pk` 로 둔다 (`noise_pk` 는 서명으로 보호된다).

## 봉투 평문과 재생 방지 (2026-11-09 승인)

- `ct` 는 Noise IK 메시지 1개다. 첫 메시지 (`-> e, es, s, ss`) 에 평문을 페이로드로 싣는다. 수신 쪽은 이 메시지에서 송신자 정적 키를 얻어 `/trust` 로 확인된 키와 대조한다.
- 평문 (암호화 전, UTF-8, JSON 한 줄, 키 순서 고정):
  `{"v":1,"ts":<unix 초>,"nonce":"<32 hex>","text":"<본문>"}`
  - `text` 길이와 제어 문자 처리는 기존 규칙 (수신 쪽에서 `clean_text`, 2000자).
  - `nonce` 는 난수 16바이트의 소문자 hex.
- nonce 와 시각은 암호문 안에 있어서 공개 채널에서 보이지 않고 바꿀 수도 없다.
- 수신 검사 순서: 봉투 검증 (`relay::open`) → 복호화 (송신자 정적 키 확인) → JSON 형식 → `v == 1` → `|ts - now| <= 300` → `nonce` 재사용 거부 → 표시. 실패는 모두 조용히 버린다.
- 재생 방지 캐시: 메모리에 `nonce` 와 `ts` 를 보관한다 (`relay_replay.rs`). 상한 10,000개. 시간창 밖 항목은 정리한다. 상한에 도달하고 시간창 안의 항목이 가득 차 있으면 새 봉투를 거부한다 (살아 있는 nonce 는 밀어내지 않는다).
- 한계: 캐시는 재시작 시 비워진다. 따라서 **시간창 300초 안에서만 재생이 가능하다.** 300초가 지난 봉투는 시각 검사에서 거부된다. 재시작 직후 300초 안에 캡처한 봉투는 한 번 더 표시될 수 있다.

## 상대 입력 ID (짧은 ID v3, 2026-11-09 요청)

- 상대 칸 (Ctrl+R 설정, 안드로이드 `/relay`) 은 **짧은 ID 8자 (소문자 `[a-z0-9]`)** 만 받는다. 64자 공개키 입력은 없다.
- 조회는 한 번만 한다: `GET {url}/rest/v1/peers?short_id=eq.<id>&select=pk,name,noise_pk,short_id`. 행이 1개가 아니면 "상대를 찾지 못함". 조회로 얻은 `pk` 와 `noise_pk` 를 그 뒤로 쓴다.
- 짧은 ID 는 찾기용일 뿐 신원이 아니다. 신뢰는 `/trust` 지문 비교로만 한다 (두 Noise 키로 계산한 코드).
- 각 기기의 짧은 ID: PC 는 state 폴더 `short-id.txt` (0600, 처음 한 번 만든다), 안드로이드는 SecureStore. 설정 화면과 `/relay` 화면에 크게 보인다. 공개키 (64자) 는 그대로 보인다.
- 등록 (put-peer v3): 서명 문자열 `herdr-talk-put-v3\n<pk>\n<noise_pk>\n<short_id>\n<name>\n<ts>\n<nonce>` (줄바꿈 `\n`, 끝 줄바꿈 없음). 본문 순서 `pk, noise_pk, short_id, name, ts, nonce, sig`.
- 중복: `short_id` 가 다른 `pk` 에 있으면 함수가 `409` 를 준다. 클라이언트는 새 ID 를 만들어 다시 보내며 최대 5회. 같은 `pk` 의 재등록은 같은 ID 를 유지한다.
- 기존 값: `relay.json` 의 `peer` 가 8자 ID 가 아니면 (예: 예전 64자 키) 무시하고 빈 값으로 읽는다. 설정 화면에서 다시 입력한다.
- 소유자 작업: `0002_short_id.sql` 실행 전에 `short_id` 가 없는 행을 지운다 (주석 참고), `put-peer` 재배포.

## 연결 방식 선택 (2026-11-09 요청)

- 방식은 둘 중 하나만 쓴다 (동시 사용 아님). 설정 파일 `relay.json` 의 `mode` 키.
  - `local` (기본): 기존 LAN 동작 그대로. relay 를 시작하지 않는다. 행 게시·조회 없음.
  - `supabase`: 메시지 송수신은 relay 로만 한다. 평문도 암호문도 LAN 으로 보내지 않는다. LAN 으로 온 채팅 본문은 표시하지 않는다.
- LAN 발견 (`peers` 목록) 은 두 방식 모두 유지한다 (화면 표시용). `supabase` 에서는 발견된 피어로 메시지를 보내지 않는다.
- `mode` 가 없거나 알 수 없는 값이면 `local`. 기존 파일에 relay 값이 있어도 자동으로 켜지지 않는다. 사용자가 고른다.
- `supabase` 를 고른 채 `url`, `key`, `name`, `peer` 중 하나라도 비어 있으면 저장을 거부하고 이유를 보여 준다.
- 쓸 때는 `mode` 를 항상 기록한다. 설정 화면 (Ctrl+R) 맨 위 줄에서 고른다.
- 화면: TUI 와 GUI 모두 Ctrl+R 설정 화면 하나에 방식 선택 줄 (맨 위) 과 Supabase 항목이 있다. GUI 상단의 "연결 방식" 버튼은 같은 화면을 연다. 첫 실행 (`mode` 없음) 에는 선택 화면이 먼저 뜬다 (TUI 는 30초 후 로컬/자체로 시작하고 저장하지 않는다. GUI 의 시간 제한은 아직 없다).
- 설정 화면에서 "저장" 은 완전한 설정만 받는다 (빠진 항목 이름을 보여 주고 저장하지 않는다). "닫기" / Esc 는 저장하지 않고 나간다.

## 채널 접근 제어 (2026-11-09 결정: 공개 채널 유지)

- Realtime 채널은 **공개 채널** (`private: false`)로 쓴다. 구독에 Auth 가 필요 없다.
- 보안은 채널 이름의 비밀성에 기댄다. 채널 이름은 두 X25519 공개키의 해시다 (`relay.rs` `channel_name`).
  - 이름을 아는 사람은 누구나 암호문을 받을 수 있다. 복호화는 할 수 없다.
  - 메시지 단위 인증은 Realtime 에 없다. 봉투 검증 (`relay.rs` `open`) 과 Noise 가 막는다.
  - 스팸·과부하를 막는 장치는 현재 없다. 한도는 Supabase 쪽 설정으로만 조정 가능하다.
- 사용자 고지 문구: "relay 채팅 내용은 종단 암호화되지만, 대화 상대 쌍과 접속 시각은 서버에 보입니다."
- 비공개 채널 (Auth 필요) 은 나중에 Auth 를 도입할 때 재검토한다.
