# relay 여러 상대 연결 계획 (3명 이상 대화)

- 작성: 2026-11-11 (chef). 상태: **계획만. 구현 전.** 사용자 승인 뒤 dev 에 단계별로 요청한다.
- 관련: [supabase-relay.md](supabase-relay.md) (현재 설계), [encryption-protocol.md](encryption-protocol.md), [todo.md](todo.md).

## 1. 지금 안 되는 것

2026-11-11 실제 확인: 파이썬, 러스트, 안드로이드 앱 셋이 한 방에서 대화할 수 없다.

- supabase 모드에서 노드는 `relay.json` 의 `peer` **한 명**하고만 연결한다 (`relay_chat.rs` `run`: `find_peer(config, &settings.peer)`).
- 채널 이름이 두 노드 키의 해시라서 채널 하나에 두 명만 들어간다 (`channel_name(내 키, 상대 키)`).
- supabase 모드에서는 LAN 상대에게 보내지 않는다 (테스트 `supabase_mode_sends_nothing_to_lan_peers`).
- 그래서 가능한 조합은 "PC 노드 여러 개 (모두 local)" 또는 "노드 둘 (relay 1:1)" 뿐이다.

## 2. 목표와 범위

- 목표: supabase 모드에서 한 노드가 **여러 상대**와 대화한다. 예: 파이썬 + 러스트 + 앱.
- 범위: Rust (TUI, GUI 공통 `talk-core`), Python, 안드로이드 앱. 네 곳이 같은 동작을 한다.
- 범위 밖: 파일 전송, 메시지 저장, supabase 와 LAN 을 동시에 쓰는 혼합 모드, 서버 쪽 방(room) 개념.

## 3. 방식 비교

| 방식 | 내용 | 서버·와이어 변경 | 평가 |
|---|---|---|---|
| **A. 쌍별 채널 여러 개 (추천)** | 상대마다 지금과 같은 1:1 채널을 하나씩 맺는다. 보낼 때 상대 수만큼 각각 암호화해 보낸다. | 없음 (와이어 v1, 테이블, Edge Function 그대로) | 변경이 가장 작다. 종단 암호화와 `/trust` 규칙이 그대로 유지된다. |
| B. 그룹 채널 + 그룹 키 | 방 하나에 모두 들어가고 그룹 키로 암호화한다. | 와이어 v2, 그룹 키 배포·교체 규칙, 새 벡터 | 멤버 추가·제거 때 키 교체가 필요하다. 설계와 검증 부담이 크다. |
| C. 중계 노드 | PC 노드 하나가 받은 메시지를 다른 상대에게 다시 보낸다. | 없음 | 중계 노드가 평문을 본다. "서버와 제3자는 평문을 보지 않는다" 원칙과 맞지 않는다. |

**A 를 추천한다.** 이유: 서버와 와이어 형식을 건드리지 않고, 기존 테스트 벡터가 그대로 유효하다.

## 4. A 방식 설계

### 4.1 설정 (`relay.json`)

- 새 항목 `peers`: 상대 short ID 목록 (8자, 소문자 영문·숫자). 예: `"peers": ["vf3x480l", "yhg03edu"]`.
- 기존 `peer` (문자열 하나) 는 계속 읽는다. `peers` 가 없으면 `[peer]` 로 본다. 저장할 때는 `peers` 로 쓰고, 옛 판이 읽을 수 있게 `peer` 에 첫 항목도 같이 쓴다.
- 검증: 항목마다 기존 `valid_short_id`. 자기 short ID 는 거부한다 (2026-11-11 에 자기 ID 를 넣어 `not connected` 가 난 사례가 있다). 중복 제거.
- 상한: 8명 (결정 필요, 6번).

### 4.2 연결

- 상대마다 지금 `run` 루프가 하는 일을 한다: `find_peer` → `/trust` 확인 → `channel_name` → 구독.
- 한 상대가 실패해도 (행 없음, 미확인, 접속 실패) 다른 상대는 계속 동작한다.
- WebSocket 은 가능하면 하나를 쓰고 그 위에 채널을 여러 개 연다. 지금 `Link` 가 채널당 소켓 하나인지 확인이 필요하다 (7번).
- `leave` (나갈 때 자기 행 삭제) 는 그대로다. 행은 노드당 하나다.

### 4.3 보내기와 받기

- 보내기: 확인된 (`/trust`) 상대 전원에게 각각 Noise 로 암호화해 보낸다. 미확인 상대에게는 보내지 않고, 누구에게 안 갔는지 한 줄로 알린다.
- 받기: 채널마다 기존 `receive` 와 같다. 보낸 사람 이름은 지금처럼 확인된 이름으로 표시한다.
- **방이 아니다.** 내가 보낸 글은 내 `peers` 에 있는 사람만 받는다. A 가 B·C 를 넣고, B 가 A 만 넣었으면 B 와 C 는 서로 글을 못 본다. 셋이 다 보려면 셋 모두 나머지 둘을 넣어야 한다 (완전 연결). 이 점을 설정 화면과 문서에 적는다.

### 4.4 화면

- 상태 줄: `relay: connected` 대신 `relay: 2/3` (연결된 수 / 설정한 수). 실패한 상대의 이유는 `/peers` 에서 본다.
- `/peers`: relay 상대도 줄마다 보여 준다 (이름, short ID, 상태: 연결됨 / 미확인 / 행 없음 / 재시도 중).
- 설정 화면 (TUI·GUI `Ctrl+R`, Python, 앱): 상대 ID 입력을 한 줄에서 목록으로 바꾼다 (추가, 삭제).

## 6. 결정 필요 (사용자)

1. 방식: A (쌍별 채널) 로 갈지.
2. 상대 수 상한: 8명 제안.
3. "방이 아니다" 동작 (4.3) 을 받아들일지. 방처럼 보이게 하려면 B 방식이 필요하다.
4. 앱도 이번 범위에 넣을지, PC 판을 먼저 할지.

## 7. 확인 필요 (구현 전 dev 조사)

- `Link` (Rust), Python WebSocket 클라이언트, 앱 `client.ts` 가 소켓 하나에 채널 여러 개를 열 수 있는지. 안 되면 상대 수만큼 소켓이 필요하고 Supabase Realtime 동시 접속 한도에 영향이 있다.
- Supabase 무료 한도 (동시 접속 수, 메시지 수) 에서 8명 완전 연결이 문제없는지. 소유자 계정에서 확인.
- 재전송 방지 캐시 (`NonceCache`) 를 상대별로 둘지 하나로 둘지.
- 한 상대의 `find_peer` 가 응답하지 않을 때 다른 상대 연결이 늦어지지 않는지 (지금 루프는 순차).

## 8. 위험

- 메타데이터: 서버는 지금도 누가 누구와 대화하는지 안다. 상대가 늘면 그 관계가 더 많이 보인다. 고지 문구를 갱신한다.
- 부분 연결 혼동: 일부만 서로 넣으면 대화가 엇갈려 보인다. 화면에 "이 글은 N명에게 보냄" 을 표시하는 방법을 검토한다.
- 호환: 옛 판 노드는 `peers` 를 모르고 `peer` 첫 항목만 쓴다. 섞어 써도 1:1 은 그대로 된다.
